# AGENTS.md

MIGO (Miagao Incident Gateway for Operations): MDRRMO Miagao's incident intake system. Residents report through chat; responders triage on a web dashboard.

Read the [PRD, TRD, sitemap, and data model](https://docs.google.com/document/d/1DcYYP8369BnRDyPKTOIHHp2Qaja-y59i-i9gSGF-Hfk/edit?usp=sharing) before designing a feature, adding a table, or choosing a library.

Tasks live in GitHub issues.

## Repo

pnpm + Turborepo. Run scripts from the root (`pnpm <script>`), or one package with `pnpm --filter <name> <script>`.

- `apps/api`: NestJS 11 modular monolith, Drizzle, Better Auth
- `apps/web`: React + Vite, TanStack Router/Query, Tailwind, shadcn
- `packages/shared` (`@repo/shared`): Zod schemas and types used by both apps. Zod is its only dependency; server-only code (Drizzle schema, auth config, prompts) and React components stay in their app.

## API

- ESM: relative imports end in `.js` (`./health.module.js`).
- One NestJS module per domain under `src/`, matching the TRD module list. Controllers stay thin; logic lives in services.
- Validate input with nestjs-zod DTOs built from `@repo/shared` schemas.
- Every route requires a session through Better Auth's global guard. Mark public routes with `@AllowAnonymous()` and restrict roles with `@Roles([...])`.
- Env vars are declared and validated in `src/config/env.ts`; add new ones there and to `.env.example`.
- Version pins are deliberate: NestJS 11 (nestjs-zod lacks 12 support), TypeScript 5.9, drizzle-orm 0.45.x.

## Database

- Drizzle owns every table, including Better Auth's, so `drizzle-kit` is the only migration tool. The exception is Chat SDK's `chat_state_*` tables: the SDK creates them, drizzle-kit ignores them, and they hold no records.
- Update `docs/database.md` in the same PR as any schema change.
- `src/database/schema/auth.ts` is generated. After changing auth config or plugins, run `pnpm --filter api auth:generate`, then `pnpm db:generate`.
- Generate migrations locally with `pnpm db:generate`; each one is reviewed SQL in `apps/api/drizzle/`. After a rebase that brings in someone else's migration, delete yours and regenerate.
- PostGIS columns are `geometry` in SRID 4326 through the `customType`s in `schema/columns.ts`; spatial queries use the `sql` template.
- Records are permanent: record every correction in `ReportEdit` and retire rows through status (e.g. `invalid`), never `DELETE`.

## Web

- File-based routes in `src/routes/`; `routeTree.gen.ts` is regenerated by the Vite plugin.
- Add UI primitives with `pnpm dlx shadcn@latest add <component>` (lands in `src/components/ui/`).
- Import from `src/` with the `@/` alias.

## Verifying

- Run `pnpm lint && pnpm typecheck && pnpm test && pnpm build` before calling work done.
- For web changes, load the affected page in a browser and check the console; a 200 on `index.html` proves nothing about module resolution.

## Git

- Conventional Commits, enforced by commitlint: `type(scope): concise description`. Add a body only when the subject can't carry the why.
- Each commit is one atomic, self-contained change. Inspect the staged diff before committing so it holds only intended changes.
- Commits carry no co-author or agent attribution.
- Hooks and GPG signing always run. If signing fails because GPG is locked or needs input, stop and ask the user to unlock it.
- Existing commits stay as they are; amend, rebase, reset, or otherwise rewrite history only when the user asks.
- Update a branch from its base by rebasing.

### Branches

- One branch per issue or logical change, cut from `main`; work never lands directly on `main`.
- Name it `type/short-description` (`feat/web-chat`, `fix/status-token`), using `feat/` rather than `feature/`, with no issue number.

### Issues

- Create an issue when a change warrants its own tracking; one-off fixes can go straight to a PR unless the user asks for an issue.
- Follow the issue templates in `.github/ISSUE_TEMPLATE/`.
- Set the issue type (Task, Bug, Feature, Epic) and only labels that clearly apply (`resident`, `responder`, `admin`, ...).

## Pull requests

- Follow `.github/pull_request_template.md`.
- Keep PRs focused and reasonably sized.
- Add only labels that clearly apply.
- Use `Closes #<n>` for each issue the PR fully resolves; reference partly addressed issues without a closing keyword.
